# 0002. 이전은 고정된 9단계로 하고, 단계마다 상태 파일에 저장한다

- 상태: 채택
- 날짜: 2026-11-02

## 상황

이전은 몇 분에서 몇십 분 걸리고, 중간에 프로세스가 죽거나 운영자가 멈출 수 있다. AI가 Plan을 만들지만, 클러스터를 바꾸는 동작은 사람이 검토할 수 있는 고정된 코드로만 해야 한다. 리허설에서는 한 단계씩 실행해 보고, 플랫폼은 단계 사이에 사람 승인이나 카나리를 끼워 넣을 수 있어야 한다.

## 결정

- 단계는 precheck, prepare, presync, delta, fence, switchover, cutover, verify, finalize 아홉 개로 고정한다(`engine.Steps`). Plan은 단계를 더하거나 순서를 바꿀 수 없고, 값만 정한다.
- 단계 하나를 실행하는 `RunStep`과 남은 단계를 끝까지 실행하는 `Run`을 둔다. 이미 끝난 단계는 건너뛰고, 앞 단계가 끝나지 않았으면 실행을 거부한다.
- 상태는 `.hopcharlie/runs/<runID>.json`에 단계 시작, 끝, 플래그가 바뀔 때마다 저장한다. 같은 runID로 다시 열면 이 파일을 읽어 이어 간다. 다른 Plan의 run을 열면 거부한다.
- 상태에는 단계별 기록과 증거(LSN, 지연, 해시 비교 결과, 다운타임) 외에 되돌리기 판단에 쓰는 플래그(`writesHeld`, `sourceDemoted`, `promoteRequested`, `trafficOnTarget`)를 둔다.
- 진행 상황은 `Options.Emit`으로 이벤트를 내보낸다. CLI(`hopmigrate -json`)는 같은 이벤트를 JSON Lines로 출력한다.
- 엔진은 HTTP 서버가 아니다. 라이브러리(`pkg/engine`)와 CLI(`cmd/hopmigrate`)로만 쓴다.

## 검토한 대안

- Plan에 단계 목록을 적고 엔진이 해석하는 방식: 유연하지만 AI가 만든 Plan이 위험한 순서를 만들 수 있고, 원복 경계(0003)를 코드로 보장하기 어렵다.
- 상태를 DB에 저장: 여러 프로세스가 공유하기 좋지만, 엔진 CLI를 단독으로 쓰기 어려워진다. 플랫폼은 자기 DB에 기록을 따로 두고 엔진 상태 파일은 그대로 쓰기로 했다(platform ADR 0002).
- 엔진에 카나리와 승인 대기 단계를 넣기: 플랫폼이 `RunStep`으로 단계 사이에 끼워 넣기로 했다(platform ADR 0005). 엔진은 데이터 이전만 맡는다.

## 결과

- 플랫폼은 동기화(precheck~delta)와 전환(fence~finalize)을 나눠 부르고, 그 사이에 운영자 승인을 받는다. 엔진을 고치지 않고 가능했다.
- 상태 파일 저장과 외부 동작(게이트웨이 호출, CNPG patch) 사이에 프로세스가 죽으면 파일이 실제보다 한 걸음 늦을 수 있다. 재개할 때는 저장된 플래그와 실제 상태를 함께 보고 판단해야 한다. 정확히 한 번 실행을 보장하지는 않는다.
- 같은 run을 두 프로세스가 동시에 실행하는 것은 엔진이 막지 않는다. 플랫폼이 클러스터당 실행 하나만 허용해서 막는다.
- 처음 `State()`는 얕은 복사라서 `Steps`의 `*StepRecord`를 엔진과 공유했고, 단계가 도는 중에 다른 goroutine이 읽으면 data race가 났다(platform ADR 0005에서 재현). 지금은 단계 기록과 evidence map을 복사해서 돌려주므로 언제 읽어도 된다. evidence 값은 단계가 저장한 뒤 바꾸지 않으므로 공유한다.
