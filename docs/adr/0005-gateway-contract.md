# 0005. 트래픽 전환은 DNS가 아니라 게이트웨이 HTTP 계약으로 한다

- 상태: 채택
- 날짜: 2026-11-02

## 상황

쓰기 다운타임을 3분 안에 끝내고 실패 요청을 0건으로 만들려면, 전환하는 동안 들어온 쓰기를 버리지 않고 붙잡았다가 새 환경으로 보내야 한다. 전환 시점은 엔진이 데이터 상태를 보고 정해야 한다. 엔진은 게이트웨이 구현과 따로 개발되므로 둘 사이에 계약이 필요하다.

## 결정

- 엔진은 게이트웨이에 다음 HTTP 요청만 보낸다(`pkg/gateway`). 토큰이 있으면 `Authorization: Bearer`를 붙인다.

  | 요청 | 의미 |
  | --- | --- |
  | `GET /healthz` | 200이면 정상 |
  | `POST /v1/writes/hold` | 새 쓰기를 붙잡고, 처리 중인 쓰기가 끝난 뒤 200 |
  | `POST /v1/writes/release` | 붙잡은 쓰기를 현재 backend로 보낸 뒤 200 |
  | `POST /v1/route {"backend":"eks"}` | 트래픽을 해당 backend로 돌린 뒤 200 |

- 전환 순서는 hold(fence), route와 release(cutover)다. 원복할 때는 route를 원본으로 한 다음 release한다.
- hold가 2xx로 끝났을 때만 쓰기를 붙잡았다고 기록한다. 2xx가 아닌 응답은 모두 실패로 본다.
- 게이트웨이 없이 리허설할 때는 Plan에 `"gateway": {"mode": "none"}`을 쓴다. 이때는 쓰기를 막지 않으므로 누락 0건을 주장할 수 없다.
- backend 이름은 기본값으로 Plan의 `source.env`, `target.env`를 쓴다.

## 검토한 대안

- DNS 전환: TTL 때문에 전환 시점을 통제할 수 없고, 쓰기를 붙잡을 수도 없다.
- 엔진이 Kubernetes Service나 Ingress를 직접 바꾸기: 클러스터 사이 전환에는 클러스터 밖에 진입점이 하나 필요하다.
- 엔진이 앱을 scale 0으로 내려 쓰기를 막기: 그 사이 요청은 실패한다.

## 결과

- 이 계약은 플랫폼의 게이트웨이(`platform/cmd/gateway`)가 그대로 구현했다. 세부 동작(hold 원자성, 최대 보류 시간, 쓰기는 엔진만 옮김)은 platform ADR 0004에 있다.
- 게이트웨이의 drain 시간(기본 30초)보다 엔진 HTTP 타임아웃(60초)이 길다. hold가 drain 중에 끊기지 않는다.
- 엔진이 보류 중에 죽으면 보류는 풀리지 않는다. 게이트웨이의 최대 보류 시간과 운영자의 release가 대신한다.
