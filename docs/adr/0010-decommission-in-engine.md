# 0010. 이전 완료 판정과 원본 정리(decommission)는 엔진 저장소의 별도 실행기로 만든다

- 상태: 채택
- 날짜: 2026-11-02

## 상황

엔진의 9단계(0002)는 데이터를 옮기고 검증한 뒤 finalize로 끝난다. 그런데 "이전이 끝났다"고 말하려면 두 가지가 더 필요하다는 팀 의견이 나왔다.

- 남은 의존성: 새 환경이 아직 원본에 기대고 있지 않은지. 새 앱 설정에 옛 주소가 남았는지, 실제로 원본에 접속하는지, 원본을 막아도 주문·조회·업로드가 되는지.
- 남은 리소스: 원본 쪽 리소스가 정리됐는지. 중지하거나 막아도 리소스는 남아 있는 것이고, 롤백용으로 일부러 남기는 것(지금도 옛 DB를 replica로 남긴다)은 따로 표시해야 한다.

이 판정을 어디서 할지 정해야 했다. 후보는 엔진 저장소와 platform 저장소였다. platform은 이미 카나리와 승인 대기를 엔진 밖에서 처리한다(platform ADR 0005).

## 결정

- 완료 판정과 원본 정리는 엔진 저장소가 책임진다. 이전 엔진 담당이 이전의 시작부터 완료 판정까지 맡는다.
- 이전 9단계에는 넣지 않는다. 같은 run에 붙는 별도 실행기 `decommission`으로 만든다. 이전 run이 `succeeded`일 때만 시작할 수 있고, 상태는 run과 같은 디렉터리에 따로 저장한다. 이전 단계의 계약(0002)과 원복 경계(0003)는 바뀌지 않는다.
- 엔진은 측정을 직접 다 구현하지 않는다. 게이트웨이, DB, 쿠버네티스 API에서 근거를 받아 통과·중단을 판단하고 기록한다. 측정 대상은 포트 인터페이스 뒤에 둔다(0007).
- 순서는 고정한다.
  1. inventory: 원본 네임스페이스에서 앱 소유 리소스 목록을 만든다(Plan의 라벨 셀렉터에 맞는 쿠버네티스 리소스와 원본 CNPG Cluster).
  2. stop: 옛 앱 워크로드를 0으로 줄이고 CronJob을 멈춘다. 원래 값은 annotation에 남겨 되돌릴 수 있게 한다. 옛 앱은 원래 옛 DB에 붙어 있으므로, 먼저 멈춰야 남은 접속이 새 환경이나 다른 곳의 의존성이라고 말할 수 있다.
  3. observe: 정해진 시간 동안 원본으로 가는 접속을 센다. 옛 DB의 클라이언트 세션(엔진 자신 제외)과 게이트웨이의 원본 backend 요청 수다. 측정하지 못한 항목은 0이 아니라 "측정 안 함"으로 남긴다.
  4. block: 옛 앱과 옛 DB 파드로 들어오는 접속을 NetworkPolicy로 막는다(CNPG 오퍼레이터만 허용). 옛 DB는 새 primary를 계속 복제하므로 롤백할 수 있다. 엔진이 옛 DB에 실제로 접속하지 못하는 것까지 확인한다.
  5. smoke: 원본을 막은 상태에서 사용자 입구(게이트웨이)로 Plan에 적은 조회·쓰기 요청을 보내 확인한다.
  6. reconcile: 같은 기준으로 다시 조회해 리소스를 중지, 의도적 보존, 삭제 승인 대기, 미처리로 나누고 리포트를 만든다. 옛 CNPG Cluster와 PVC는 롤백용으로 보존한다. 삭제는 이번 범위에서 하지 않고 사람 승인 대기로 둔다.
- `decommission -undo`로 차단을 풀고 워크로드를 원래 수로 되돌린다. 반대 방향 이전(롤백) 전에 쓴다.
- 리포트는 "0건" 하나로 줄이지 않는다. 미처리 수, 의도적 보존 수와 사유, 관찰 시간과 그동안의 원본 접속 수, 차단 테스트 결과와 검사 범위를 따로 내보낸다. 콘솔은 이 값을 그대로 보여 준다.
- 실패하면 차단을 풀고 멈춘 워크로드를 되돌린다. 데이터는 이미 새 환경에 있으므로 이전 자체를 되돌리지는 않는다. 되돌리기는 운영자가 반대 방향 이전으로 한다.

## 검토한 대안

- platform에 만들기: 카나리처럼 운영 절차로 볼 수 있다. 그러나 옛 DB의 세션 확인, CNPG 상태, 차단처럼 엔진이 이미 가진 어댑터를 다시 만들어야 하고, 완료 판정 책임이 두 저장소로 나뉜다.
- 이전 9단계 뒤에 단계를 더하기: 한 번에 끝까지 돌릴 수 있다. 그러나 관찰 시간이 몇 분씩 걸리고 클라우드 API 실패가 이전 결과를 흐리게 한다. 데이터 이전이 성공했는데 정리가 실패했다고 run 전체가 실패로 보이면 안 된다.
- 하지 않기: 데모에서 "남은 리소스 0건"을 근거 없이 보여 주게 된다. 이는 No Mock 규칙에 어긋난다.

## 결과

- 이전 run의 결과(`succeeded` 등)는 지금 의미 그대로다. 완료 판정은 decommission 리포트로 따로 본다. 콘솔과 platform은 두 결과를 구분해서 보여 줘야 한다.
- 원본 접속이 0건이어도 관찰한 시간과 범위 안에서만 0건이다. 배치 작업처럼 드물게 도는 의존성은 놓칠 수 있으므로, 리포트에 관찰 시간과 검사 범위를 같이 적는다.
- 1차 범위는 쿠버네티스와 CNPG, 게이트웨이다. 클라우드 VM, RDS, IAM 같은 클라우드 자원 목록은 어댑터를 추가해 넓힌다.
- platform은 decommission 시작 API와 이벤트를 새로 받아야 한다. 계약은 구현 전에 platform 담당과 정한다.
- 로컬 kind(CNPG 1.25.1, kindnet)에서 실제로 돌렸다. 성공한 이전 run 뒤에 옛 앱(Deployment 2개 파드, CronJob, Service, ConfigMap, Secret)과 옛 CNPG Cluster를 대상으로 했다.
  - 통과: 미처리 0, 중지 2, 보존 2(옛 Cluster와 PVC), 삭제 승인 대기 3. 30초 관찰 동안 옛 DB 클라이언트 세션 0, 게이트웨이 원본 요청 0. 차단 뒤 약 7초 만에 엔진의 옛 DB 접속이 거부됐고, 스모크 요청 2개가 통과했다. 차단 뒤에도 옛 DB는 healthy였고 새 primary를 streaming으로 따라가 새 쓰기를 받았다(롤백 가능).
  - 실패: 새 환경 쪽 배치가 옛 DB에 세션을 붙잡고 있자 observe가 "세션 1개"로 실패했고, 옛 앱(2개)과 CronJob이 원래대로 돌아갔으며 차단 정책은 남지 않았다.
  - `-undo`로 차단이 풀리고 옛 앱이 2개로 돌아왔다.
