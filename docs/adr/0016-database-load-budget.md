# 0016. 운영자 부하 정책으로 이전 작업을 제한하고 검증을 배치 처리한다

- 상태: 채택
- 날짜: 2026-11-07

## 상황

복제 연결의 포트를 분리해도 운영 PostgreSQL의 CPU, 디스크 읽기와 WAL 부담은 공유된다. 기존 검증은 전체 PK를 메모리에 모았고 대상 테이블을 다시 읽었다. 부하가 높거나 관측이 불가능한 상황에서도 다음 이전 단계가 시작될 수 있었다.

## 결정

서버 환경 변수 `HOPMIGRATE_LOAD_POLICY`가 가리키는 운영자 소유 JSON에서 Prometheus URL, 양쪽 `env/namespace/cluster`별 쿼리와 임계값을 읽는다. 사용자 Plan으로 URL이나 쿼리를 받지 않는다. CPU 비율, IO 지연, 여유 디스크 바이트와 WAL 바이트를 필수로 관측한다. 실제 원본 scrape 시각을 별도로 조회하고, 누락·복수 결과·비정상 수·오래된 관측은 실패 처리한다. 토큰, 쿼리와 응답 본문은 이벤트에 넣지 않는다.

CPU/IO 초과는 새 작업 시작 전에 제한 시간 동안 대기한다. 디스크/WAL 위험은 즉시 실패한다. 진행 중 prepare/presync/delta 등의 취소 가능한 작업은 주기적으로 확인하여 엔진 작업을 취소한다. 쓰기 차단 전 양쪽 부하를 새로 확인하되, 쓰기 차단부터 promotion/cutover까지 관측 복구를 기다리지 않는다. promotion 요청 후 실패는 기존 원칙대로 halt하며 원본을 자동 승격하지 않는다.

누락 검증은 읽기 전용 repeatable-read cursor로 최대 1,000개씩 읽고, 대상에는 PK 실제 타입의 동등 조건으로 조회한다. 전체 PK 집합을 저장하지 않는다. 배치 키 자료는 8 MiB, source snapshot은 30분으로 제한한다. PK 외 NOT NULL domain이 있어도 기존 대상 행을 타입 변환의 기본값으로 사용하며 빈 대상은 모든 원본 키가 누락된 것으로 판정한다. 성공 쓰기 기록도 타입 기반 개별 조회와 배치별 대기를 사용한다. 쿼리 실패나 중단은 미완료이며 누락 0의 근거가 아니다.

쓰기 차단 중 정확한 count/hash 검증은 유지한다. 정책의 쿼리 제한 시간을 전체 fence 검증에 적용하며 배치 대기는 하지 않는다. 정책 미설정 시 지표 기반 가드는 비활성이고, PK 배치 검증의 기본 쿼리 제한은 5초다.

## 검토한 대안

- 포트 분리만 사용: 운영 DB 자원 경쟁을 제한하지 못한다.
- 실행 중 WAL replay 중지: 원본 WAL 적체와 디스크 위험을 키울 수 있어 제외했다.
- CNPG에 무조건 `pg_basebackup --max-rate` 옵션 추가: 사용 중인 안정 버전 CRD에서 지원하지 않는 필드를 넣을 수 없다. [CNPG 개발 버전 문서](https://cloudnative-pg.io/docs/devel/bootstrap/)와 [1.28 API](https://cloudnative-pg.io/docs/1.28/cloudnative-pg.v1/)를 구분한다.
- 전체 PK를 텍스트로 변환하여 대상 전체 조회: 검증 자체의 메모리와 반복 IO 부담 때문에 배치 및 타입 기반 조회로 교체했다.

## 결과

부하 승인과 엔진이 실행하는 검증의 작업 단위를 제어한다. OS 자원 상한이나 실행 중인 물리 복제 속도를 강제로 제한하는 기능은 아니다. CNPG가 이미 시작한 base backup/streaming은 엔진 대기 취소만으로 중단되지 않는다. 실제 Prometheus 및 운영 CNPG에서의 부하 감소율은 아직 측정하지 않았다.

cursor가 유지하는 snapshot은 vacuum에 영향을 줄 수 있으며 전체 읽기량은 사라지지 않는다. 대형 테이블의 정확한 count/hash는 제한 시간 내 끝나지 않으면 실패한다. 운영자는 실제 지표와 용량에 맞는 정책을 제공해야 하며, 임계값 초과 후 진행 중인 복제 정리는 별도 운영 절차가 필요하다. 설정과 한계는 [운영 안내](../db-load-budget.md)에 기록한다.
